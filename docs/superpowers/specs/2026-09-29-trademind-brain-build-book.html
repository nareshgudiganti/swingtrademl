Before you start

How to use this book

This book turns the v5 platform picture into things we can build one at a time. It is written for two readers: the owner and Claude. Each section starts in plain words, and the technical detail follows.

If you are the owner

  • Read Part A (four short sections) to see the whole idea.
  • Use the module index to pick what to build next. The build plan in section 17 shows what must come first.
  • Ask for one module at a time: “Take M03 and finish it, then start the local server.”
  • Each module sheet ends with a green “Done when you see” box. That is your check.

If you are Claude, building a module

  • Read section 10 (module contract) and section 12 (data contracts) first. They do not change per module.
  • Build only what the module sheet lists. Never edit another module's internals; talk through contracts.
  • Always write the fallback and the contract tests, even if the module is simple.
  • Never touch the live trading path of version 1 unless the sheet says so (only M18 does).

Part A · Understand

1 · What we are building

A brain that looks at the market every day, understands the situation, remembers what happened in similar situations, and makes a clear, explained decision for each stock, while a safety layer keeps it inside hard limits.

Today's bot already does part of this. It reads prices, runs a machine-learning model, checks risk limits and places paper trades. But the thinking is spread across files and happens in one fixed chain: if one part is missing, the chain breaks. The brain puts the thinking into eight named steps with fixed contracts between them, so that each step can be improved, switched off or replaced on its own.

The three promises of this design

1 · Build one module at a time

Every module has its own sheet in Part D. You can ask for any module whose dependencies are done, and check it on your own computer when it is finished.

2 · Works with modules missing

Each step has a fallback. If the memory module is not built, the brain says “no past experience” and carries on. It is more careful, never broken.

3 · Safety is never optional

The risk and safety gate is the one mandatory module. If it is missing or fails, the brain says NO NEW TRADES. Existing exits keep running regardless.

What stays exactly as it is

  • Version 1 keeps trading. The current strategies, exit loop (every 60 seconds), risk limits and Kite integration are not modified by any module except M18, which is the switch you control.
  • The locked trade rules. Target +8%, stop −4%, up to 15 trading days, a 15% drawdown halt, a 25% sector cap and taking half off at the first target (+5%).
  • Paper first. The brain runs in shadow until its record justifies trusting it, then goes through a manual-approval phase before any automatic live trading.

3 · Design principles

Twelve rules that every module follows. When a module sheet and a principle seem to disagree, the principle wins, and the module sheet gets corrected.

#PrincipleWhat it means in practice
P1Contracts firstModules talk only through the data contracts in section 12. A module can be rewritten completely as long as its contract holds.
P2Every step has a fallbackA step never raises an error to the brain. Off, failing, too slow or fed stale data means that step's fallback answer is used and the reason is recorded.
P3Missing knowledge makes the brain more carefulA fallback can only make a decision more cautious (TRADE→WATCH→WAIT), never bolder. Missing modules can never create a trade.
P4Safety is mandatoryM07 must run for any TRADE to leave the brain. Its absence means NO NEW TRADES. Exits never depend on the brain.
P5Wrap, don't rewriteWorking code (features, models, risk checks, limits, exit policy) is called from the brain, not copied or rewritten.
P6Version 1 is untouchedThe brain runs beside v1. Only M18 connects the brain to execution, and only when the owner switches it.
P7Shadow before trustNew modules start in shadow mode. They are switched on only after their recorded output has been checked.
P8Only data known at the timeEvery input carries an as_of time. Replays use only what was known then, which prevents look-ahead bias.
P9One vocabularyTRADE / WATCH / WAIT / AVOID for ideas, HOLD / MONITOR / REDUCE / EXIT for holdings, NORMAL / DEFENSIVE / NO NEW TRADES for the market. No other decision words anywhere.
P10Every decision explains itselfA decision carries plain-English reasons and a trace of which modules ran, which fell back and why.
P11Evidence, not promisesExpected returns are shown as a track record: “reached +8% in 41% of 120 similar signals”, never “you will make 8%”.
P12Learning proposes, the owner approvesNo module changes rules, thresholds or models by itself. It writes a proposal; the owner accepts or rejects it.

Why P3 matters most. The user wanted the brain to “work as intended” even if some modules are never started. P3 is what makes that safe: a brain with fewer modules is a more cautious brain, not a broken or reckless one.

Part C · Solution design

9 · How the brain thinks

A brain run is like a careful trader's evening routine: look at the data, understand the market, recognise the situation, remember similar times, form opinions, check the rules, decide, and later learn from what happened.

Technically, a run passes one object, the brain context, through the eight steps. Each step reads what earlier steps wrote and adds its own part. Nothing is passed around informally: if it is not in the context, a later step cannot see it.

9.1 The three kinds of run

Run kindWhenUniverseStepsResult
nightly15:50 IST on trading daysWatchlist (20–30) + holdings1–7 (8 runs at 16:30 separately)Tomorrow's decisions, banner, holding reviews
intradayEvery 15 min, 09:30–15:15Holdings only1, 2, 6, 7 (M15 adds tracking)HOLD / MONITOR / REDUCE / EXIT updates, drift alerts
whyOn demandOne stock1–7A full trace for the console or a card's “why?” link

9.2 Step modules and plug-ins

Each step has one step module that owns the step's result, and any number of plug-ins that add to it. For example, step 2 (state) is owned by M03, which builds the state object; the market brain (M10) and sector brain (M11) plug into it and fill in the market and sector parts. If M10 is off, M03 still produces a basic market state from the existing regime classifier. If M03 is off too, the step fallback gives “unknown” and the brain goes DEFENSIVE.

9.3 How the brain reaches v1 execution

The brain is registered as one more strategy in the existing registry: @register_strategy class BrainStrategy with strategy_type = "brain". Its evaluate() reads the stored brain decision for that stock and returns a normal SignalDecision (TRADE → BUY with stop, target and horizon). Created as a shadow strategy, its signals are recorded and scored like any other but never traded. M18 flips it from shadow to active when the owner approves. This reuses the whole execution, risk and exit machinery of v1 without changing it.

Part C · Solution design

10 · The module contract

Every module, however simple, has the same outside shape. This is what makes “take this module and finish it” possible: the builder only needs this contract, the module sheet, and the data contracts.

10.1 The interface

# backend/src/swing_trade_ml/brain/module.py
class Mode(StrEnum):
    ON = "on"          # output is used
    SHADOW = "shadow"  # runs, output recorded in the trace, not used
    OFF = "off"        # not run; step fallback applies

class Step(StrEnum):
    PERCEIVE = "perceive"; STATE = "state"; RECOGNISE = "recognise"; REMEMBER = "remember"
    REASON = "reason"; RISK = "risk"; DECIDE = "decide"; LEARN = "learn"

@dataclass(frozen=True, slots=True)
class Manifest:
    id: str                    # "M03"
    name: str                  # "State engine"
    step: Step
    kind: Literal["step", "plugin"]
    version: str               # module version, "1.0.0"
    reads: tuple[str, ...]     # contract names with major version: ("Snapshot@1",)
    writes: tuple[str, ...]    # ("MarketState@1", "StockState@1")
    budget_s: float = 10.0     # nightly time budget; intraday uses budget_s / 10
    mandatory: bool = False    # only M07 sets this
    default_mode: Mode = Mode.SHADOW

class BrainModule(ABC):
    manifest: ClassVar[Manifest]

    @abstractmethod
    def run(self, ctx: ContextView) -> Contribution:
        """Read only what the manifest declares; return only what it declares."""

    def health(self, ctx: ContextView) -> Health:
        return Health.ready()

MODULE_REGISTRY: dict[str, type[BrainModule]] = {}

def register_module(cls: type[BrainModule]) -> type[BrainModule]:
    MODULE_REGISTRY[cls.manifest.id] = cls
    return cls

10.2 The runner

# brain/runner.py (simplified)
def run_brain(req: RunRequest, db: Session) -> BrainContext:
    ctx = BrainContext.start(req, reader=DatedReader(db, as_of=req.as_of))
    for step in STEPS_FOR[req.kind]:
        used = False
        for mod in registry.modules_for(step, db):            # step module first, then plug-ins
            if mod.mode is Mode.OFF:
                ctx.trace.skipped(mod, "switched off"); continue
            try:
                out = with_budget(mod.run, ctx.view_for(mod), mod.budget(req.kind))
                contracts.validate(out, mod.manifest.writes)
            except BudgetExceeded:   ctx.trace.fallback(mod, "too slow");        continue
            except ContractError as e: ctx.trace.fallback(mod, f"bad output: {e}"); continue
            except Exception as e:   ctx.trace.fallback(mod, f"error: {e!r}");   continue
            if mod.mode is Mode.SHADOW:
                ctx.trace.shadow(mod, out); continue
            ctx.merge(out); ctx.trace.used(mod); used = True
        if not used:
            ctx.merge(FALLBACKS[step](ctx)); ctx.trace.step_fallback(step)
    constitution.enforce(ctx)                                  # section 15; cannot be skipped
    store.save_run(db, ctx)
    return ctx

10.3 Rules for module builders

  • Read through the view. ctx.view_for(mod) exposes only the contracts listed in reads. Database access goes through DatedReader, which never returns rows after as_of.
  • Write a Contribution. A contribution is a small object holding lists of contract records. The runner merges it; modules never mutate the context directly.
  • Merge rules are per contract. States: plug-ins fill their own sub-part (market, sector…). Opinions: appended. Verdicts: only M07. Decisions: only M08 (or the step fallback). Later-running plug-ins cannot overwrite an earlier module's fields.
  • No side effects in run(). No orders, no Telegram, no writes to v1 tables. Storing the run is the runner's job. Alerts are M16's job, after the run.
  • Contract versions. A breaking change to a contract bumps its major version (Opinion@2). The registry refuses to start a module whose reads are not produced by any module or fallback.
  • Folder per module. brain/modules/m03_state/ with module.py, logic.py (pure functions), and tests/.

11.3 The monotonic rule

The constitution pass (section 15) enforces one simple ordering so that no combination of modules can produce a bolder decision than the full brain would allow:

AVOID < WAIT < WATCH < TRADE  ·  EXIT < REDUCE < MONITOR < HOLD

A fallback or a failing check may move a decision to the left, never to the right. A test (NFR-03) proves this on a stored day by switching each module off in turn and comparing.

14.1 Priorities

  1. Exits first. v1's check_exits keeps its own job and never waits for the brain.
  2. Owner actions next. Halts and overrules are applied immediately and also stored in the next run.
  3. Runs never overlap. A run lock (Redis key brain:lock:{kind}) prevents two runs of the same kind; a late run is skipped and logged, not queued.
  4. Retries. A failed nightly run retries once after 5 minutes, then alerts the owner. Module errors are not retried within a run; the fallback is used.

Only one module must be built on its own first: M00, the core. After that, work runs in waves. Modules inside a wave do not depend on each other and can be built at the same time; each wave needs the one before it.

17.1 What “parallel” means in practice

  • One builder (one Claude session at a time): build the wave's modules one after another in any order. Parallel just means the order inside a wave doesn't matter.
  • Several builders at once: each module gets its own branch and git worktree (brain/m06-reasoning). They only share brain/contracts.py, which M00 fixed. A module that needs a contract change stops and asks.
  • Merging: each module merges into a brain integration branch after its tests and local check pass; the integration branch is rebased on main regularly. Nothing reaches production until the owner merges to main, and even then BRAIN_ENABLED=false keeps it idle.

20.1 The monotonicity test

def test_turning_any_module_off_never_makes_decisions_bolder(golden_day):
    full = run_brain(golden_day.request, modes=ALL_ON)
    for module_id in registry.optional_modules():
        reduced = run_brain(golden_day.request, modes=ALL_ON | {module_id: Mode.OFF})
        for symbol, d in reduced.decisions.items():
            assert rank(d.word) <= rank(full.decisions[symbol].word), (module_id, symbol)

20.3 Replay checks before switching a module ON

  • Replay at least 60 trading days with the module ON and OFF.

  • A module is switched ON when it does not reduce hit rate and does not increase drawdown, or when it only adds information (cards, tracking) without changing decisions.
